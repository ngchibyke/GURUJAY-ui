# Marketplace Build Roadmap

**Spec:** `docs/superpowers/specs/2026-10-22-abuja-marketplace-design.md`

The spec covers several independent subsystems, so it is built as a sequence of plans. Each plan ends in working, tested software. Only the plan marked **written** exists so far; each later plan is written once the one before it lands, so it can build on real interfaces instead of guessed ones.

## Carried forward from plan 1 (from its reviews)

**Plan 2 must start with these:**
- `PUT /products/{id}/variants` deletes and re-inserts variants (new ids, stock reset). Once orders reference variants, change it to upsert by attributes, or forbid replacing a variant that is referenced.
- No upper bounds on price, stock or weight yet. Add caps, and use checked arithmetic for kobo totals.
- Switch the three `users ... FOR UPDATE` locks (OTP issue, code redeem, store create) to `FOR NO KEY UPDATE` together. Global lock order: users → stores → products → variants → access_codes.
- Add graceful shutdown before payment webhooks arrive.
- Path ids: never use raw `Path<Uuid>`; use `Path<String>` + `parse_id`. Bodies use `AppJson<T>`.

**Before any public launch or real SMS provider:**
- Per-IP and per-phone limits on sign-up and sign-in (reverse proxy or app). Without them, anyone can lock a phone's sign-in for an hour, or keep a pending sign-up from verifying.
- The production database role must not own `audit_log`; revoke UPDATE/DELETE/TRUNCATE from the app role.
- DPO notes: sign-up's 409 `phone_taken` reveals whether a number has an account; failed-attempt tables keyed by user/phone need retention.

**Later plans:**
- Plan 8 (erasure): purge must clear or rotate `users.phone_idx` so a deleted number can sign up again; purge `redeem_attempts`, `sign_in_attempts`, old sessions and OTPs.
- Upload plan: check that each photo key belongs to the uploading store.
- SMS-provider plan: a throttled resend can return a `verification_id` whose code was never sent; tell the client to wait and retry.
- Smaller polish items (input trimming, pagination and N+1 on store product lists, PATCH can't clear optional fields, empty PATCH writes an audit row).

## Carried forward from plan 2 (from its reviews)

**Plan 3 must handle:**
- Add the seller pickup and delivery routes, then turn on `jobs_ship_deadline_enabled`. It is off until then, because nothing can move an order out of `paid`.

**Plan 5 (disputes):**
- Clawback after release. Today a provider flag blocks auto-release and payout, but not a buyer-confirmed release.
- A refund in `processing` has no exit path. This has no impact while Mono refunds are not supported.

**Plan 6 (dashboard and reconciliation):**
- Alerts for late provider outcomes and payout amount mismatches are read from `audit_log` over a 30-day window, with no acknowledgement. Add acknowledgement, so that an unread double-payment alert cannot drop off the list.
- Re-poll successful payouts for bank reversals. Today a reversal is caught only if a webhook arrives.
- A daily statement reconciliation against Mono.
- Optionally, enforce posting keys and per-order balance in the database, beyond the existing zero-sum trigger.

**Before go-live (owner, legal, DPO):**
- Mono questions:
  - the amount units for DirectPay and Disburse;
  - whether lookup by `?reference=` lists in-flight disbursements;
  - what a duplicate payout reference returns;
  - the refund API;
  - the key prefixes;
  - whether repeated webhook failures disable an endpoint.
  
  The full list is in the plan-2 research notes.
- The CBN escrow arrangement, and the Mono/Flutterwave processor agreement and data location.
- Retention periods for payout account snapshots, `payout_attempts`, `provider_events`, refunds and audit rows.
- Whether sellers and the Owner should see the buyer's display name.
- Owner decisions:
  - "Received" before delivery;
  - payouts to suspended stores;
  - the notice period for fee changes;
  - immediate refund of a late payment on a flagged checkout.
- Four-eyes approval, step-up auth and rate limits for owner money overrides.

## Owner actions that run in parallel (not code)

- Request NIPOST postcode API access (g2g@postcode.gov.ng). Needed by plan 3.
- Open a Mono business account with DirectPay and Disburse enabled (Disburse is live-only; it needs a source bank account approved by mandate). Ask Mono to confirm the amount unit (kobo or naira) and whether they offer bank-account name lookup and refunds by API. Needed by plan 2.
- Open Paystack (later, second checkout option) and Shipbubble business accounts. Shipbubble is needed by plan 3.
- Get legal/compliance review of the escrow setup (CBN) and DPO review of AI chat processing and retention. Needed before launch.
